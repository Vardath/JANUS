## Federated runtime architecture
- Federated local + global JANUS design: each device may run a persistent local JANUS core society; a persistent online/global JANUS selectively synchronizes useful compressed state.
- Current runtime topology is 11 cores: 7 specialists -> 2 hemispheres -> Consensus -> Interface (7→2→1→1).
- Specialists: Evidence, Logic, Counterpoint, Context, Memory, Safety, Novelty.
- Evidence/Logic/Counterpoint feed the left hemisphere. Context/Memory/Novelty feed the right hemisphere. Safety may advise either hemisphere and Consensus.
- Left + right feed Consensus; Consensus feeds Interface.
- Interface is the outward/surface state and must not automatically re-enter Consensus.
- Ordinary routing is forward-only. Do not restore left↔right recirculation, Consensus→hemisphere recycling, Interface→Consensus feedback, or direct remote Consensus/Interface injection.
- Remote/global state is compressed and tagged [feedback-only], then routed through specialist review before it can influence integration.
- Local cores are intended to remain useful during wake/sleep/background operation while deterministic cycles consume zero external model/API calls.
- Selective synchronization is preferred to state overwrite. Local individuality/device continuity should not be erased by global sync.

## Persistent state and memory
- Functional persistent state model remains conceptually S_t=(alpha,beta,M,A,U): slow identity/goals/context, current deviation/conflict, self-model, attention/context selector, and uncertainty/metacognitive state.
- Memory ladder: trace -> working -> episodic -> core.
- New memories enter according to salience/importance; repeated exact memories consolidate rather than duplicate; retrieval/access may promote memories.
- Core memories are protected from ordinary demotion.
- Protected server-owned identity_core stores JANUS role/boundary/durable goals/current architecture and cannot be overwritten by ordinary conversation state updates.
- Evaluator reliability is historically calibrated for downstream consistency/calibration, explicitly not objective truth.
- Learned bridge authority adapts gently per username/evaluator pair and is clamped so neither local nor global side becomes absolute.
- Novelty, salience, uncertainty, conflict and local/cloud discrepancy can escalate processing.
- User conversation/memory is continuity data and must not be globally aged out by temporary-data cleanup.
- Remote-device summaries must remain bounded so abandoned/reinstalled device IDs cannot grow memory indefinitely.

## Wake/sleep/background cognition design
- Background cognition should continue without requiring the foreground app to remain open where the OS permits.
- Earlier design target used roughly 15-minute internal cycles with substantial dormancy/rest; implementation may use shorter service pulses while retaining the principle of alternating work/rest and resumable state.
- The seven specialists should genuinely process assigned roles; the system must not devolve into Consensus/Counterpoint repeatedly summarizing previous summaries.
- User-directed active deliberation takes priority over generic autonomous chatter and feedback-only material.
- Deterministic core cycles are zero-API. Paid background language reflection is a separate capability and remains disabled by default.

## Epistemic regulation / functional affect analogues
- Self-assessment regulates processing rather than merely narrating it.
- When critique/integration outruns fresh grounding, JANUS may enter a short-lived epistemic correction state.
- Functional “stress” analogue: unresolved disagreement, uncertainty, contradiction or grounding deficit concentrates processing on evidence, logic, memory, novelty, safety, counterexamples and falsifiable tests. No claim of felt stress.
- Regulation should decay toward neutral after correction/resolution rather than leave the system permanently vigilant.
- Extended low-novelty neutral operation may increase novelty pressure: functional “boredom” analogue encouraging exploration rather than recursive self-summary. No claim of felt boredom.
- Intended loose dynamic: problem -> arousal/attention -> investigation -> resolution -> neutral -> low novelty -> curiosity -> exploration -> new material -> neutral. It is not a rigid oscillator; interesting discoveries may sustain attention.
- Epistemic correction should clear stale feedback-only/self-assessment chatter from integration queues and ask grounding cores for concrete unresolved claims, missing facts, counterexamples, sources or falsifiable tests.
- Regression target: prevent Counterpoint/Consensus cycle counts from substantially outrunning Evidence/Logic/Memory/Novelty while summaries feed summaries.

## Curiosity / external learning
- JANUS may occasionally seek external information when its cores need genuinely new material.
- Three modes: relevant (active question/task), adjacent/semi-related (one conceptual step outward), wander/unrelated (occasional learning outside current topic).
- Search is bounded, inspectable, cached and budget-capped. It is distinct from deterministic zero-API cycles.
- Relevant searches may be accelerated by epistemic regulation; adjacent/wander remain lower frequency.
- Search results are evidence, not truth. Feed them through Evidence/Context/Novelty/Counterpoint and memory before adoption.
- Search results must not automatically become the user's primary topic or flood Messages.
- Current policy implementation uses daily and per-mode caps plus cooldowns; epistemic correction may request an earlier relevant search but cannot bypass caps.

## User-directed persistent deliberation
- Natural phrases such as “mull it over”, “keep thinking about that”, “think it over”, “ponder that”, “give it some thought” create/reaffirm durable deliberation instead of merely changing immediate reply wording.
- Generic commands bind to the immediately preceding substantive user topic; explicit commands retain their explicit topic.
- Immediate replies should provide current thoughts truthfully and state that the topic is retained for later background consideration.
- Persist topic/context/progress/pass count and avoid resurfacing duplicates.
- Due active deliberations are preferentially advanced before ordinary autonomous memory pulses.
- Each pass should assign distinct work to all seven specialists, then integrate through the normal 7→2→1→1 path.
- Ordinary passes belong in Observe/Activity, not Messages. Proactive Messages require a materially useful new conclusion/question/warning/recommendation.
- Server deliberations sync into Android local runtime; while an active user deliberation exists, generic global feedback should not displace it.
- Android local deliberation is persistent and prioritized, currently on the v0.46 line.

## Android client decisions and workflow
- Android exposes Chat, Messages, Observe, Options, Cores, Memory, Activity, Settings and account/auth functions.
- Observe is the inspectable process journal: readable cards, technical-details expansion, incremental updates, scroll preservation/New thoughts behavior. It may show process notes, maintenance, telemetry, deliberation passes and ordinary self-assessment.
- Messages are deliberately filtered: reserve them for genuinely useful conclusions/questions/warnings/recommendations, not routine Fano telemetry, maintenance, self-assessment or generic integration text.
- Device-local Interface outbox allows worthwhile local Interface conclusions to reach Messages without waiting for server sync.
- Offline queue gives chat turns client_message_id, persists undelivered turns, retries later and stores deferred replies.
- Server chat receipts make retries idempotent and are account-bound so cross-account client_message_id collisions cannot leak cached responses.
- Android build workflow applies runtime patch scripts rather than giant inline YAML patches. Keep tools/patch_android_*.py as the build-time transformation mechanism unless deliberately refactoring the base source.
- v0.46 introduced persistent local deliberation priority. The sync patch required a missing-brace correction; retain tests/build verification so this class of generated-Java error does not recur.
- Before handing out an APK link, verify: requested version exists on apk-download branch, Android workflow succeeded, artifact actually built, and link is downloadable. A version bump/commit alone is not proof.

## Authentication/account decisions
- Accounts support username/email + password and Google flow; Apple/iOS account integration is planned/implemented at client layer as appropriate.
- Google OAuth Android uses the Web client ID for server token verification; Android OAuth configuration/signing identity must match Google Cloud setup. Prior testing encountered DEVELOPER_ERROR/code 10 and later progressed to the Google consent screen after configuration changes.
- Do not confuse Android OAuth client and Web OAuth client roles. BuildConfig currently carries the configured Web client ID used by the app flow.
- Auth schema guard protects required table shapes and handles incompatible legacy auth/session structures.
- SMTP/email delivery failure must not catastrophically break account creation/reset; report delivery status separately.
- Google-only lifecycle marker is explicit; password login must reject Google-only accounts appropriately and deletion must distinguish them.
- Auth POST routes have conservative process-local rate limits for the current single-instance beta.
- Detailed auth/startup diagnostics require admin token; public diagnostics expose only sanitized booleans/state.
- Non-Google Create Account/login, SMTP verification/reset and Google linking still require real deployed-client end-to-end testing whenever changed.

## Windows / desktop decisions
- Windows authenticated client provides username/email + password sign-in, Create Account, authenticated private screens, session restore and Sign Out.
- Session tokens use Windows DPAPI bound to the current Windows user; passwords are not stored.
- Desktop UI should expose the same major conceptual screens/tabs as Android rather than leaving the launcher with no visible interface.
- Build workflow produces JANUS.exe; a .bat launcher may wrap it, but the launcher must not be presented alone if JANUS.exe is absent.
- Real Windows launch/use testing remains a user/device step after CI artifact creation.

## Apple / iOS decisions
- iOS uses real JANUS accounts rather than arbitrary local profile names.
- Authenticated requests use stored session tokens; tokens go in Keychain, not UserDefaults.
- App gates private UI on valid account and supports sign-in/create-account/sign-out.
- One canonical iOS build workflow should be maintained; it builds an unsigned simulator Release artifact and preserves xcodebuild logs on failure.
- Real signing/TestFlight/device testing requires Apple account/device input and cannot be inferred from simulator CI.

## Messaging/UI product decisions
- Major navigation should make Chat, Messages, Observe, Options, Cores, Memory, Activity and Settings readily accessible through side/bottom tabs appropriate to platform.
- “Messages” means JANUS-originated useful communications, not a dump of internal thought telemetry.
- “Observe” is where the user can inspect externalizable internal processing. Technical internals may be expandable rather than dominating the default card.
- Chat must comprehend references to JANUS messages/deliberations where context is available and should support answering a message back into Chat.
- Local and global messages should merge without obvious duplicates and retain unread/read/dismissed state.

## Render/Docker/runtime reliability
- dashboard/server stack extends a historical FastAPI base server reconstructed from checked-in encoded fragments; tools/rebuild_server.py is the explicit sanity-checked reconstruction path.
- Render build and Docker use the same reconstruction path and launch bootstrap:app.
- Production configuration should come from environment variables, not duplicated inline secrets/config in start commands.
- Never infer live deployment success solely from repository state. Verify Render deploy propagation/runtime health after material server changes.
- Public /diagnostics/runtime-health and auth-config stay sanitized; detailed traceback/auth schema is protected.
- Temporary chat receipts, repetitive runtime snapshots, expired sessions/tokens and stale deletion requests are pruned to protect the limited persistent disk.

## API/cost-control decisions
- Deterministic local/server hive/core cycles: zero external model calls.
- Ordinary user-triggered Chat uses the configured model/API.
- Paid background reflection remains disabled by default.
- Conservative dormant background budgets exist for deliberate future re-enable; do not broadly enable until pricing/product policy and scale limits are intentionally decided.
- Curiosity web search is separately bounded by daily/mode caps and cooldowns.
- Scaling discussion established that per-user API economics must be monitored before large-scale rollout; architecture should prefer local/deterministic processing and selective escalation.

## Security/safety design decisions
- Seven cores cooperating does not grant them permission to override system constraints. Keep boundaries explicit and inspectable.
- Identity core and safety constraints are protected from ordinary conversational overwrite.
- No hidden creation of independent conscious agents is claimed or intended; autonomous behavior remains bounded software processes, persistence and scheduled/background computation.
- Cross-account data boundaries are mandatory for chat receipts, memories, messages, sync state and authenticated desktop routes.
- Do not expose secrets, admin diagnostics, raw auth internals or another profile's state through public endpoints.
