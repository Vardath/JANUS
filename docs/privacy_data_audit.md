# JANUS Privacy and Data Audit

Status: release-readiness audit for Android/Google Play preparation.
Last updated: 2026-08-20.

This document is the canonical inventory of personal/user data handled by the current JANUS Android app and global server. It is intended to drive the Privacy Policy, Google Play Data Safety answers, account-deletion verification, and future security reviews. It must be updated whenever JANUS adds a new SDK, analytics system, advertising system, external service, database table, permission, identifier, or user-data flow.

## 1. Current Android permissions

The Android manifest currently requests only:

- `android.permission.INTERNET` — required to communicate with the JANUS global server and Google identity services.
- `android.permission.POST_NOTIFICATIONS` — used for JANUS background/outbox notifications.

The app does not currently request contacts, precise/coarse location, camera, microphone, phone/SMS, calendar, storage/media, Bluetooth, accessibility, VPN, or advertising-ID permissions.

## 2. Account and identity data collected

JANUS may collect and store:

- Username/display identity.
- Email address.
- Password credential material for password-backed accounts. Plaintext passwords are not stored; the server stores PBKDF2-SHA256 password hashes with per-password random salts and a high iteration count.
- Google account subject identifier (`google_sub`) when the user chooses Google Sign-In.
- Email-verification state.
- Internal immutable numeric account ID.
- Account creation time and account-disabled state.

Purpose: authentication, account ownership, continuity across devices, account recovery, and account administration.

## 3. Authentication/session data

JANUS stores:

- Random session tokens on the client so a signed-in user can stay signed in.
- Only SHA-256 hashes of session tokens on the server.
- Session creation and expiry timestamps.
- One-time email verification and password-reset tokens; only token hashes are stored server-side, with purpose, creation time, expiry time, and used state.

Password reset invalidates existing sessions. Account deletion removes sessions and auth tokens through database foreign-key cascades.

## 4. Conversation and JANUS memory data

The server stores user-scoped application data including:

- User chat messages.
- JANUS chat responses.
- JANUS memory records, including role, content, memory level, and creation time.
- Activity/events generated by conversation and JANUS processing.
- JANUS proactive/outbox messages and their read/dismissed state.
- Externalizable background reflection/process summaries.
- Reflection-promotion state used to avoid repeatedly surfacing the same background material.

Current application tables include `desktop_memory`, `desktop_events`, `janus_message_state`, and `janus_reflection_promotion`.

Purpose: provide chat, persistent JANUS continuity, memory, background processing, outbox/messages, and user-visible activity/history.

## 5. Data sent to OpenAI

When the user sends a JANUS chat message, the global server may send to OpenAI:

- The current user message.
- Relevant recent JANUS conversation/memory context selected by the server.
- JANUS system/instruction text required to produce the response.

When paid/cloud background reflection is enabled, the server may also send recent JANUS records to OpenAI to generate a concise externalizable background process note. The local seven-core wake/sleep cycle itself is designed not to make external model/API calls.

OpenAI receives this data as a service provider for AI response generation. JANUS does not currently send account passwords, raw session tokens, or Resend API credentials to OpenAI.

## 6. Data sent to Google

If the user selects Google Sign-In:

- Android Credential Manager/Google identity services handle the Google account-selection and identity-token flow.
- JANUS receives a Google ID token and sends it to the JANUS server.
- The server validates the token against Google's verification infrastructure/client identity.
- JANUS stores the Google subject identifier and verified email needed to link the Google identity to the JANUS account.

JANUS does not currently use Google Analytics, Firebase Analytics, AdMob, or Google advertising identifiers in the audited Android code.

## 7. Data sent to the transactional email provider

When transactional email is activated, JANUS may send to the configured SMTP/transactional email provider:

- Recipient email address.
- Verification or password-reset email content.

JANUS currently has SMTP support prepared for Resend. Production sending remains dependent on a verified sending domain/sender configuration.

## 8. Data stored locally on the Android device

The Android app uses app-private local storage/SharedPreferences and WebView local storage for items such as:

- Current JANUS profile/username display value.
- JANUS access/session token.
- Internal account ID.
- UI preferences such as refresh settings.
- Last-notified JANUS message/event identifier.

The app code also contains a fallback based on `Settings.Secure.ANDROID_ID` for a legacy/local profile identifier when no saved profile exists. Under the current authenticated design, server-side private-data ownership is based on the signed-in account/session, not on this Android identifier. This fallback should be reviewed for removal before production if it is no longer required.

## 9. Notifications

JANUS can schedule a roughly 15-minute Android WorkManager task that checks the signed-in user's JANUS outbox using the authenticated session and may display a notification for a new unread JANUS message.

Notification content can include JANUS-generated message text. Users should therefore be warned that notification previews may reveal JANUS content on the device lock screen depending on their Android notification settings.

## 10. Public account-deletion request data

The public `/delete-account` workflow can collect:

- Email address submitted by a person requesting account deletion.
- Request timestamp.
- Request status.

A public request does not immediately delete the account solely on knowledge of an email address; ownership must be verified before processing.

## 11. Account deletion scope

Authenticated in-app account deletion currently removes:

- The `accounts` row.
- Associated server sessions.
- Associated authentication/reset/verification tokens.
- Matching pending deletion requests.
- Known user-profile rows in `desktop_memory`.
- Known user-profile rows in `desktop_events`.
- Matching `janus_message_state` rows.
- Matching `janus_reflection_promotion` rows.

The deletion implementation is intentionally explicit. Every future table containing user-scoped data must be added to the deletion audit and deletion routine before release.

## 12. Current data not collected by JANUS app code

The audited Android/server code does not currently implement:

- Advertising or ad-personalisation data collection.
- Sale of personal information.
- Precise or approximate location collection.
- Contacts/address-book collection.
- Photos, videos, audio recordings, camera, or microphone capture.
- SMS or call-log collection.
- Health/fitness data collection.
- Payment-card or banking-data collection.
- Advertising ID collection.
- Firebase/Google Analytics telemetry.
- Third-party behavioural analytics SDKs.

This statement applies to the audited JANUS code and must be revisited if third-party SDKs are added.

## 13. Security controls observed in the current implementation

- TLS/HTTPS is required for Android server traffic; cleartext traffic is disabled in the Android manifest.
- Passwords are salted and hashed rather than stored in plaintext.
- Session tokens are random; only token hashes are stored server-side.
- Private desktop/JANUS endpoints derive authority from a valid server session rather than a client-supplied username.
- Google ID tokens are server-verified before account linking.
- Password reset invalidates existing sessions.
- Account deletion requires an authenticated session and, for password-backed accounts, current-password confirmation.
- Secret deployment credentials are configured as environment variables and must not be committed to the public repository.

## 14. Retention model

Current behaviour is primarily user-controlled/persistent rather than time-limited:

- Conversation, memory, activity, and outbox records persist until explicitly deleted or future retention rules are implemented.
- Sessions expire after approximately 30 days unless explicitly invalidated earlier.
- Email-verification tokens expire after approximately 24 hours.
- Password-reset tokens expire after approximately 30 minutes.
- Account-deletion request records persist until processed/removed.

A production Privacy Policy should state these behaviours accurately. A future release may benefit from formal retention periods for stale logs, deletion requests, and low-value memory/event records.

## 15. Google Play Data Safety working classification

Based on current code, the likely Play Data Safety categories that require disclosure include:

- Personal info: name/username and email address.
- App activity: app interactions and user-generated content/conversation content.
- App info/performance only if future telemetry/crash reporting is added; none is intentionally implemented in this audit.
- Device or other identifiers: review the legacy `ANDROID_ID` fallback before final submission. If retained/used beyond local fallback behaviour, disclose it appropriately.

Primary purposes include app functionality, account management, authentication, developer communications/transactional account email, and AI service delivery.

The final Play Console answers must be checked against the exact shipping APK/AAB and every third-party SDK present at submission time.

## 16. Release blockers/findings from this audit

1. **Production transactional email is not yet live** until JANUS has a verified sending domain/sender. Password recovery and email verification code exist, but delivery cannot be considered production-complete without it.
2. **Review/remove the legacy `ANDROID_ID` fallback** before release unless there is a clear functional need. Authenticated JANUS ownership no longer depends on it.
3. **Define a production retention policy** for conversation/memory/activity data and deletion-request records rather than leaving retention implicit forever.
4. **Re-run this audit immediately before Play submission**, including Gradle dependencies and the final AAB, because any analytics/crash-reporting/ads SDK added later changes disclosure obligations.
5. **Notification privacy wording** should be included in the Privacy Policy or app help because proactive JANUS message previews may appear outside the app.

## 17. Audit boundary

This document describes the JANUS repository code and configured architecture as audited on the date above. It is not legal advice and does not replace jurisdiction-specific review. The Privacy Policy and store declarations must describe the actual production deployment, third-party processor terms, developer identity, and any later functionality added after this audit.
